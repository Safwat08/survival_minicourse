Training a Survival Model on 3D MRI

4.1 Survival from Medical Images argued that a survival model is an imaging backbone with a different head and a different loss. This section is that claim made concrete: a full walkthrough of taking a cohort of 3D MRI volumes with per-subject survival labels and finetuning a self-supervised backbone on them.

Mapped onto the backbone/head picture:

Abstract (see 4.1 Survival from Medical Images) Concrete (this tutorial)
Imaging backbone the self-supervised S3D ResEnc checkpoint you finetune from
Embedding z the pooled feature vector the backbone emits per volume
Survival head whatever model.survival_loss.name selects (step 7)
Survival loss one of ten shipped losses: nll, cox, deephit, …
Evaluation Val/C-index, plus the KM and Brier curves the trainer logs

The code lives at https://github.com/Safwat08/MedSurvival3D. Every file path below is relative to a clone of that repository, and step 1 starts by making one.

It assumes you’re comfortable with Python and a shell but have never seen this codebase. The steps use placeholder names (mydataset, a modality of your choosing, generic column headers) and mark the spots you need to edit. Any cohort of 3D MRI with a clinical table works the same way; substitute your own paths, headers, and filename patterns as you go.

Steps 3 through 5 (staging, labels, preprocessing) are the work. Everything else is two commands.

This tutorial leans on concepts covered earlier in the course. If any of these are unfamiliar, read the linked section first; none take long.

Imaging vocabulary

If you arrived from the survival-analysis side of the course, these terms appear throughout and are assumed rather than explained by the codebase.

Term What it means
NIfTI (.nii.gz) The standard container for a 3D medical volume: a voxel array plus a header giving physical spacing and orientation.
Voxel spacing The physical size of one voxel in mm. Scanners differ, so volumes are resampled to a common spacing (here 1 mm isotropic) before training.
Skull stripping / brain extraction Removing non-brain tissue, leaving a brain mask. Used both to crop the field of view and to restrict intensity normalisation. HD-BET is the tool used here.
Z-score normalisation Standardising intensities to zero mean, unit variance. MRI intensities have no absolute units, so this is mandatory, not optional.
Patch A fixed-size sub-volume (e.g. [64,64,64]) cropped from the full volume at each training step. Whole 3D volumes rarely fit in GPU memory.
Blosc2 (.b2nd) A compressed chunked array format. Preprocessing writes these once so training does not repeat the expensive resample/crop/normalise work every epoch.
nnU-Net raw layout A filename convention, <case_id>_<XXXX>.nii.gz, where XXXX is a zero-padded modality index. The preprocessing tier expects it.
Hydra The config system. YAML files compose into one run config, and any key can be overridden from the command line as key=value.
Fold One train/validation partition of a cross-validation split. Training loops over folds; each subject is held out exactly once.

0. What the training code actually reads

medsurvival3d never touches raw scans. It trains on preprocessed volumes, resampled to a common spacing, brain-cropped, z-scored, and serialised as Blosc2 .b2nd tensors, alongside two small JSON sidecars. Everything below exists to produce the layout that SurvivalData.__getitem__ (src/medsurvival3d/data/survival.py) expects:

<DATA_ROOT>/
├── <IMAGE_DIR>/            # one Blosc2 file per case:  <case_id>.b2nd  → shape [C, X, Y, Z]
├── survival_labels.json    # { "<case_id>": {"event": 0|1, "time_years": <float>}, ... }
└── splits.json             # [ {"train": [...ids...], "val": [...ids...]}, ... ]  (one entry per fold)

Four things to know before you start:

  • <IMAGE_DIR> is just a config key (data.module.image_dir). Name it anything.
  • event is 1 when the event (death, say) was observed and 0 when the subject was right-censored, meaning the event hadn’t happened by last follow-up. This is the \delta of 1.2 Censored Data.
  • The label loader in survival.py accepts time_years, time_months, or time. We’ll emit time_years.
  • case_id must be identical across the .b2nd filename, the label keys, and the split lists.
ImportantMismatched case_ids are the number one cause of crashes

The same identifier has to appear in three places: the .b2nd filename, the keys of survival_labels.json, and the id lists in splits.json. Step 3 and step 4 must derive it identically. Step 5b gives you a check that catches a mismatch in seconds instead of twenty minutes into a run.

1. Setup

On the GPU box:

git clone https://github.com/Safwat08/MedSurvival3D.git
cd MedSurvival3D

Everything below runs from that directory. Then:

export PATH=$HOME/.local/bin:$PATH        # uv on non-interactive shells
uv venv --python 3.12
uv pip install -r requirements.txt
uv pip install -e .                       # gives you medsurvival3d-train / -infer
./.venv/bin/python -c "import torch, pycox, torchsurv, blosc2, nnunetv2, HD_BET; \
print(torch.__version__, torch.cuda.is_available())"

If that prints False, or a run later dies saying your NVIDIA driver is too old, your torch wheel was built for a newer CUDA than the driver supports. Check nvidia-smi for the driver’s CUDA version and reinstall to match; for 12.8:

UV_HTTP_TIMEOUT=900 uv pip install torch torchvision \
  --index-url https://download.pytorch.org/whl/cu128 \
  --reinstall-package torch --reinstall-package torchvision

You also need the S3D ResEnc backbone checkpoint that training finetunes from, e.g. checkpoint_final.pth. Note its path; it goes in model.chpt_path at step 6.

2. Bring your data

Per subject you need one or more 3D MRI volumes as NIfTI (.nii.gz), whether T1, T1-contrast, T2, FLAIR, or whatever you have, plus a survival label, meaning a follow-up time and an event/censoring flag, usually sitting in a clinical CSV keyed by subject id. Step 3 is where you decide which modality actually goes into the model.

If you’re pulling from a public archive such as TCIA and it offers a pre-skull-stripped NIfTI distribution, take that over DICOM. It makes step 5 considerably easier.

Land everything on the GPU box:

$HOME/data/mydataset/
├── raw_nifti/            # per-subject NIfTI volumes
└── clinical.csv          # survival labels

Before you script anything against this, look at what you actually have. Folder nesting and filename conventions vary wildly by source:

find $HOME/data/mydataset/raw_nifti -name '*.nii.gz' | head -20
head -1 $HOME/data/mydataset/clinical.csv        # see the real column headers

3. Stage into nnU-Net “raw” layout

The preprocessing tier (src/medsurvival3d/data/preprocessing/datasets/template_brain_preprocessing.py) wants the nnU-Net raw layout: a folder imagesTr/ in which each file is named <case_id>_<XXXX>.nii.gz, where XXXX is a zero-padded modality index (0000, 0001, and so on).

The simplest thing to do is use one modality as a single channel, with model.input_channels: 1. Pick the sequence most informative for your endpoint; see the modality table in 4.1 Survival from Medical Images. Multi-channel is a straightforward extension: stage the extra modalities as _0001, _0002, … and set input_channels to match.

Symlink your chosen modality into the _0000 slot. Set MOD to whatever token identifies that modality in your filenames, and adjust the glob and the id derivation to match what step 2 showed you (t1c here is only an example):

RAW=$HOME/data/mydataset
MOD=t1c                                                        # <- the modality token in YOUR filenames
mkdir -p $RAW/nnraw/imagesTr
for f in $(find $RAW/raw_nifti -iname "*${MOD}*.nii.gz"); do   # <- adjust the glob to your files
  case=$(basename "$f" | sed -E "s/[_-]?${MOD}.*//I")          # <- your id derivation
  ln -sf "$f" "$RAW/nnraw/imagesTr/${case}_0000.nii.gz"
done
ls $RAW/nnraw/imagesTr | wc -l     # expect one _0000.nii.gz per subject

Whatever id derivation you use here, step 4 must use the identical one.

4. Build survival_labels.json

This is the one artifact the preprocessing tier won’t create for you. You map your table’s columns onto {event, time_years}, which means settling two questions.

First, units. If your table stores days, divide by 365.25; if months, by 12.

Second, polarity.

WarningCheck the polarity of your event flag

A column named censored is the inverse of the event the model wants. Getting this backwards produces a model that trains happily, reports plausible losses, and means nothing. You will have taught it to rank the censored subjects as the high-risk ones. There is no downstream error that catches this; the only defence is reading the column definition and then checking the output of this step.

Look at your headers, then fill in the three column names:

# build_survival_labels.py  (run with your venv python, from anywhere)
import json, re
import pandas as pd
from pathlib import Path

RAW       = Path.home() / "data" / "mydataset"
IMAGES_TR = RAW / "nnraw" / "imagesTr"
CSV       = RAW / "clinical.csv"
OUT       = RAW / "survival_dataset" / "survival_labels.json"

# --- EDIT to your real headers (run `pd.read_csv(CSV).columns` to see them) ---
MOD           = "t1c"                           # the SAME modality token used in Step 3
COL_ID        = "subject_id"                    # subject identifier column
COL_TIME      = "os_days"                       # follow-up time column
TIME_TO_YEARS = 1.0 / 365.25                    # days->years (use 1/12 for months, 1.0 for years)
COL_CENSORED  = "censored"                      # flag column; values below mean "censored"
CENSORED_TRUE = {"yes", "1", "true"}            # values that mean "censored / not observed"
# ------------------------------------------------------------------------------

def norm_id(s: str) -> str:                     # must match the ids created in Step 3
    return re.sub(rf"[_-]?{MOD}.*", "", str(s), flags=re.I).strip()

staged = {p.name[:-len("_0000.nii.gz")] for p in IMAGES_TR.glob("*_0000.nii.gz")}
df = pd.read_csv(CSV); df.columns = df.columns.str.strip()   # headers often have stray spaces

labels = {}
for _, row in df.iterrows():
    cid = norm_id(row[COL_ID])
    if cid not in staged:
        continue                                             # no image staged -> skip
    censored = str(row[COL_CENSORED]).strip().lower() in CENSORED_TRUE
    labels[cid] = {"event": 0 if censored else 1,
                   "time_years": round(float(row[COL_TIME]) * TIME_TO_YEARS, 4)}

OUT.parent.mkdir(parents=True, exist_ok=True)
OUT.write_text(json.dumps(labels, indent=2))
print(f"wrote {len(labels)} labels -> {OUT}")
missing = staged - set(labels)
if missing:
    print(f"WARNING: {len(missing)} staged cases had no clinical row: {sorted(missing)}")
./.venv/bin/python build_survival_labels.py

Check three things in the output: the count should be roughly your cohort size, event should be a mix of 0s and 1s (all 1s means you inverted the censoring column), and the time_years values should be physically plausible.

The proportion of event == 1 is worth noting now, because it sets your effective sample size, not your subject count. See 1.2 Censored Data.

5. Preprocess to .b2nd

The repo’s own preprocessing produces the Blosc2 tensors and a cross-validation split file. For each case, load_crop_brainextract_normalize_images in .../datasets/template_brain_preprocessing.py resamples to the target spacing, crops a fixed field of view around the brain-mask centre, z-score normalises, and writes a .b2nd. Then generate_crossval_split (cross_validation.py) writes splits.json.

You need to adapt two things, both minor.

run_case expects a brain mask at masks/<case>_0000_bet.nii.gz, which it uses for both cropping and masked normalisation. If your NIfTI is already skull-stripped you can derive one from the nonzero voxels, as below. Otherwise call hd_bet_predict(<nnraw>) from the same module; it works on any brain MRI and needs the HD-BET weights.

The other is field of view: preprocess to a crop size at least as large as the data.patch_size you’ll train with in step 6. Below uses [128,128,128] at 1 mm with a [64,64,64] training patch.

# preprocess.py  (run with your venv python, from anywhere)
import numpy as np, SimpleITK as sitk
from pathlib import Path
from medsurvival3d.data.preprocessing.datasets.template_brain_preprocessing import (
    load_crop_brainextract_normalize_images)

RAW   = Path.home() / "data" / "mydataset"
NNRAW = RAW / "nnraw"                                   # has imagesTr/<case>_0000.nii.gz
OUT   = RAW / "survival_dataset" / "images_b2nd"

# 1) nonzero brain masks (skip if you use hd_bet_predict instead)
masks = NNRAW / "masks"; masks.mkdir(exist_ok=True)
for p in sorted((NNRAW / "imagesTr").glob("*_0000.nii.gz")):
    img = sitk.ReadImage(str(p))
    m = sitk.GetImageFromArray((sitk.GetArrayFromImage(img) > 0).astype(np.uint8))
    m.CopyInformation(img)
    sitk.WriteImage(m, str(masks / p.name.replace(".nii.gz", "_bet.nii.gz")))

# 2) resample + crop + normalize + save .b2nd, write splits.json
load_crop_brainextract_normalize_images(
    in_folder=str(NNRAW), out_folder=str(OUT),
    target_spacing=[1.0, 1.0, 1.0], patch_size=[128, 128, 128],
    brain_extract=True, num_workers=4, n_splits=3)
./.venv/bin/python preprocess.py
NoteThis step is inside the leakage boundary

Resampling, cropping and normalisation are fit per case here, so they are safe. Anything you add that is fit across cases, such as dataset-level intensity harmonisation or feature selection, must be fit on training folds only. See the leakage checklist in 4.1 Survival from Medical Images.

5b. Check what preprocessing produced

You get one <case>.b2nd per case, with every modality you staged stacked into a single [C, X, Y, Z] array, which is exactly the filename SurvivalData loads. splits.json stays where preprocessing put it, inside images_b2nd/; you point split_file at it in step 6 rather than moving it.

Now confirm the ids line up. This check saves you from a confusing crash twenty minutes into a run:

./.venv/bin/python - <<'PY'
import json, pathlib
DS = pathlib.Path.home()/"data"/"mydataset"/"survival_dataset"
lab = set(json.load(open(DS/"survival_labels.json")))
img = {p.stem for p in (DS/"images_b2nd").glob("*.b2nd")}
spl = set().union(*[set(f["train"])|set(f["val"]) for f in json.load(open(DS/"images_b2nd"/"splits.json"))])
print("labels:", len(lab), "images:", len(img))
print("labels == images:", lab == img)
print("split ids ⊆ images:", spl <= img)
PY

6. Configure and train

Configs ship as package data under src/medsurvival3d/cli_configs/. With the editable install from step 1 you edit them in place and Hydra picks up the changes live. CFG=src/medsurvival3d/cli_configs below just keeps the paths short.

Start from survival.yaml. It’s already wired to SurvivalDataModule, already single-channel, already checkpoints on Val/C-index. The only thing it lacks is a loss, which, per 4.1 Survival from Medical Images, is the one component that makes this a survival model rather than a classifier.

CFG=src/medsurvival3d/cli_configs
cp $CFG/data/survival.yaml $CFG/data/survival_mine.yaml
WarningDon’t start from a survival_<loss>.yaml

They carry a loss, but they’re wired to a different datamodule (COCACombinedB2NDDataModule), and they all set save_top_k: 0, so a run finishes having saved no checkpoint.

Add the loss under model: in survival_mine.yaml:

  survival_loss:
    name: nll

Then change five values:

Key Ships as Set to
data.module.name Survival MySurvival
data.module.data_root_dir ${data_dir}/survival_dataset ${data_dir}/mydataset/survival_dataset
data.module.image_dir nnUNetResEncUNetLPlans_3d_fullres images_b2nd
data.module.split_file ${data.module.data_root_dir}/splits.json ${data.module.data_root_dir}/images_b2nd/splits.json
data.patch_size [160, 192, 192] [64, 64, 64]

Two more depend on your cohort. data.cv.k has to match the number of folds in your splits.json; step 5 passed n_splits=3, so set data.cv.k to 3. (Both default to 5; the pair just has to agree, or training walks off the end of the splits list.) And trainer.accumulate_grad_batches ships at 48, an effective batch of 96; on a few dozen subjects that’s a wider window than you have batches, so lower it to something like 4.

TipWhy batch size matters more here than in classification

If you switch the loss to cox, effective batch size stops being a tuning knob and becomes part of the objective: the Cox partial likelihood compares each subject against the risk set of everyone still event-free, so a small batch is a poor approximation of that set. nll and the other discrete-time losses decompose per-sample and do not have this problem, a reason they are the safer default on 3D volumes. See 2.1 Cox Proportional Hazards Loss and 4.1 Survival from Medical Images.

Finally, point Hydra at writable paths. $CFG/env/local.yaml ships as placeholders:

# @package _global_
exp_dir: /home/<you>/experiments/
data_dir: /home/<you>/data/                 # so ${data_dir}/mydataset/... resolves

6b. Smoke test with fast_dev_run

Do this before any real run. It pushes one train batch and one val batch through the whole graph in about a minute and catches path, shape, and label errors while they’re still cheap.

WANDB_MODE=offline ./.venv/bin/medsurvival3d-train \
  env=local data=survival_mine \
  data.cv.k=1 data.module.fold=0 \
  model.chpt_path=/path/to/S3D/checkpoint_final.pth \
  model.save_preds=false \
  exp_dir=$HOME/experiments/smoke \
  trainer.logger.offline=true \
  +trainer.fast_dev_run=true

Don’t set seed. It defaults to False, which keeps deterministic=False, and the avg_pool3d backward has no deterministic CUDA kernel, so setting a seed crashes the run.

Success looks like `Trainer.fit` stopped: `max_steps=1` reached. and exit 0.

6c. The real run

Authenticate wandb once with ./.venv/bin/wandb login, then drop fast_dev_run and the offline flag and keep cv.k=3 to cross-validate:

./.venv/bin/medsurvival3d-train \
  env=local data=survival_mine \
  model.chpt_path=/path/to/S3D/checkpoint_final.pth \
  exp_dir=$HOME/experiments/mysurvival

medsurvival3d-train loops over the cv.k folds and streams metrics to a wandb project named after data.module.name. Checkpoints land at ${exp_dir}/${teamname}/survival/${data.module.name}/checkpoints/<run-id>/<fold>/, so with the command above, under $HOME/experiments/mysurvival/debug/survival/MySurvival/checkpoints/. The best one per fold is selected on Val/C-index. Hydra writes the run’s config.yaml to that same <run-id> directory, which is what step 8 points at.

7. Swapping the loss

The loss comes from model.survival_loss.name in your config. Ten are shipped. This is the head swap of 4.1 Survival from Medical Images, exposed as a single config key:

Name Family Covered in
cox Continuous-time proportional hazards 2.1 Cox Proportional Hazards Loss
nll, pmf, mtlr, bcesurv, pchazard Discrete-time likelihood variants 2.2 Negative Log-Likelihood Loss
deephit Discrete-time, ranking-augmented, competing-risk capable 2.4 DeepHit Loss
weibull Fully parametric 2.5 Loss Functions Compared
soft_logrank Differentiable group-separation surrogate see the caution below
composite Weighted combination of the above n/a
Warningsoft_logrank optimises the picture, not the prediction

Don’t reach for it to make a development KM plot look more separated. It optimises the later visualisation rather than the ranking, adds another weight to tune, and can overfit whichever grouping rule you happened to pick. Start with a survival objective, evaluate the continuous score honestly, and choose a cutpoint afterwards as in 3.3 Kaplan-Meier Curves.

To try a different one, copy the model.survival_loss block from $CFG/data/survival_<name>.yaml into your config. Each block encodes that loss’s own hyperparameters: deephit needs alpha and sigma, composite takes a weighted components list with a primary, and so on. If you want to sanity-check the whole install, fast_dev_run each loss the way step 6b does.

2.5 Loss Functions Compared compares these on assumptions and failure modes, which is the better basis for a first choice than sweeping all ten.

8. Reading the results

Val/C-index, the checkpoint monitor, is the survival analogue of AUC: the fraction of comparable subject pairs the model ranks in the correct risk order. 0.5 is chance, 1.0 is perfect ranking. Full treatment in 3.1 Concordance Index (C-index).

On a small cohort the C-index will be wide and noisy, and a mean near 0.5 usually means too few subjects and events rather than broken code. For a pipeline check, the right success criterion is a stable, reproducible number across folds, not a good one.

Keep censoring in mind when you interpret anything. The C-index and the KM and Brier curves the trainer logs all account for right-censoring, but your effective sample size is the number of observed events, not the number of subjects.

For per-subject risk predictions from a trained checkpoint, use the other console command, medsurvival3d-infer (src/medsurvival3d/inference/survival.py, config $CFG/inference_survival.yaml).

Its exp_dir is the run’s <run-id> directory, which holds both config.yaml and one subdirectory per fold containing the .ckpt files:

RUN=$HOME/experiments/mysurvival
UID_DIR=$(ls -d $RUN/debug/survival/MySurvival/checkpoints/*/ | head -1)   # the <run-id> dir

./.venv/bin/medsurvival3d-infer \
  exp_dir=$UID_DIR \
  splits_json=$HOME/data/mydataset/survival_dataset/images_b2nd/splits.json \
  pred_dir=$RUN/preds \
  folds=[0,1,2]

If select_best_checkpoint reports finding no checkpoints, exp_dir is pointing one level off from the fold directories.

Alongside the per-fold predictions you get preds/ensemble/. Because each fold predicts on its own held-out subjects, that table is the pooled out-of-fold result: every subject scored exactly once, by the one model that did not train on them. It covers the whole cohort, so it is the number to quote, though it is still cross-validated, not a held-out test set.

NoteNext: turning these scores into risk groups

The preds/ensemble/ table is a continuous risk score per subject. If your clinical use case needs high/low groups, 3.3 Kaplan-Meier Curves covers choosing one cutpoint on development data and freezing it, including the multiple-testing trap that makes a KM plot look better than the model is.

What has and hasn’t been run

ImportantScope of verification

Verified end to end on the target workstation: the environment install, the SurvivalDataModule data contract, and all ten losses via fast_dev_run on the S3D checkpoint (torch 2.11+cu128, torchsurv 0.2.0, Python 3.12, RTX 6000 Ada).

Verified against a real run tree: the directory layout step 8 depends on, namely config.yaml and the per-fold checkpoint directories together under a single <run-id>. They used to land in sibling directories, so if you have seen this pipeline before and remember copying config.yaml by hand, that step is gone.

Not run: the step-6 recipe builds on survival.yaml rather than the survival_<loss>.yaml configs the loss sweep used, so the specific edits in that table are read off the configs, not executed. And medsurvival3d-infer has never been run to completion; the layout it consumes is confirmed, the command is not.

Yours to run: anything depending on your data: the download, staging (step 3), the label build (step 4), preprocessing (step 5). The checks at each step are there to catch what goes wrong.
