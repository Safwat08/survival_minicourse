# Training a Survival Model on 3D MRI

[4.1 Survival from Medical Images](4.1_survival_from_medical_images.md) argued that a survival model is an
imaging backbone with a different head and a different loss. This section is that
claim made concrete: a full walkthrough of taking a cohort of 3D MRI volumes with
per-subject survival labels and finetuning a self-supervised backbone on them.

Mapped onto the backbone/head picture:

| Abstract (see [4.1 Survival from Medical Images](4.1_survival_from_medical_images.md)) | Concrete (this tutorial) |
|---|---|
| Imaging backbone | the self-supervised **S3D ResEnc** checkpoint you finetune from |
| Embedding $z$ | the pooled feature vector the backbone emits per volume |
| Survival head | whatever `model.survival_loss.name` selects (step 5) |
| Survival loss | one of ten shipped losses: `nll`, `cox`, `deephit`, … |
| Evaluation | `Val/C-index`, plus the KM and Brier curves the trainer logs |

The code lives at **<https://github.com/Safwat08/MedSurvival3D>**. Every file path
below is relative to a clone of that repository, and step 1 starts by making one.

It assumes you're comfortable with Python and a shell but have never seen this
codebase. The steps use placeholder names (`mydataset`, a modality of your
choosing, generic column headers) and mark the spots you need to edit. Any
cohort of 3D MRI with a clinical table works the same way; substitute your own
paths, headers, and filename patterns as you go.

Step 3, turning raw scans and a clinical table into what the trainer reads, is
the only part with real decisions in it. Everything else is three commands.

## Imaging vocabulary

If you arrived from the survival-analysis side of the course, these terms appear
throughout and are assumed rather than explained by the codebase.

| Term | What it means |
|---|---|
| **NIfTI** (`.nii.gz`) | The standard container for a 3D medical volume: a voxel array plus a header giving physical spacing and orientation. |
| **Voxel spacing** | The physical size of one voxel in mm. Scanners differ, so volumes are **resampled** to a common spacing (here 1 mm isotropic) before training. |
| **Skull stripping / brain extraction** | Removing non-brain tissue, leaving a **brain mask**. Used both to crop the field of view and to restrict intensity normalisation. `HD-BET` is the tool step 3 can call for this. |
| **Z-score normalisation** | Standardising intensities to zero mean, unit variance. MRI intensities have no absolute units, so this is mandatory, not optional. |
| **Patch** | A fixed-size sub-volume (e.g. `[64,64,64]`) cropped from the full volume at each training step. Whole 3D volumes rarely fit in GPU memory. |
| **Blosc2** (`.b2nd`) | A compressed chunked array format. Step 3 writes these once so training does not repeat the expensive resample/crop/normalise work every epoch. |
| **nnU-Net raw layout** | A filename convention, `<case_id>_<XXXX>.nii.gz`, where `XXXX` is a zero-padded modality index. Step 3 stages your files into it for you; you only meet it if you go off the beaten path. |
| **Hydra** | The config system. YAML files compose into one run config, and any key can be overridden from the command line as `key=value`. |
| **Fold** | One train/validation partition of a cross-validation split. Training loops over folds; each subject is held out exactly once. |

## 0. What the training code actually reads

`medsurvival3d` never touches raw scans. It trains on preprocessed volumes,
resampled to a common spacing, brain-cropped, z-scored, and serialised as Blosc2
`.b2nd` tensors, alongside two small JSON sidecars. Everything below exists to
produce the layout that `SurvivalData.__getitem__`
(`src/medsurvival3d/data/survival.py`) expects:

```
<DATA_ROOT>/
├── <IMAGE_DIR>/            # one Blosc2 file per case:  <case_id>.b2nd  → shape [C, X, Y, Z]
├── survival_labels.json    # { "<case_id>": {"event": 0|1, "time_years": <float>}, ... }
└── splits.json             # [ {"train": [...ids...], "val": [...ids...]}, ... ]  (one entry per fold)
```

Four things to know before you start:

- `<IMAGE_DIR>` is just a config key (`data.module.image_dir`). Name it anything.
- `event` is 1 when the event (death, say) was observed and 0 when the subject
  was right-censored, meaning the event hadn't happened by last follow-up. This
  is the $\delta$ of [1.2 Censored Data](../01_background/1.2_censored_data.md).
- The label loader in `survival.py` accepts `time_years`, `time_months`, or
  `time`. We'll emit `time_years`.
- `case_id` must be identical across the `.b2nd` filename, the label keys, and
  the split lists.

::: {.callout-important}
## Mismatched `case_id`s are the number one cause of crashes

The same identifier has to appear in three places: the `.b2nd` filename, the keys
of `survival_labels.json`, and the id lists in `splits.json`. Step 3 derives all
three from one source, so they agree by construction, and its `--dry-run` shows
you the id match against your clinical table before anything is written. Use it.
The alternative is a `KeyError` inside a DataLoader worker thirty minutes into a
training run.
:::

## 1. Setup

Two routes. Docker is shorter and needs nothing on the host but an NVIDIA driver.

### Docker (recommended)

```bash
git clone https://github.com/Safwat08/MedSurvival3D.git
cd MedSurvival3D
docker build -t medsurvival3d:latest .          # ~10 min, ~9 GB image
mkdir -p ~/ms3d/ckpt ~/ms3d/exp                 # create these yourself, see below
```

Every command later in this tutorial then runs inside the image:

```bash
docker run --rm --gpus all --shm-size=16g \
  --user "$(id -u):$(id -g)" \
  -v ~/ms3d/ckpt:/ckpt \
  -v ~/ms3d/exp:/exp \
  -v /path/to/your/data:/data \
  medsurvival3d:latest \
  <the command from the step you are on>
```

**The backbone downloads itself.** On the first run the container fetches the S3D
ResEnc checkpoint (852 MB) from the CC-BY-4.0 release
[`MIC-DKFZ/ResEncL-OpenMind-S3D`](https://huggingface.co/MIC-DKFZ/ResEncL-OpenMind-S3D)
into `/ckpt` and verifies its SHA-256. Use `model.chpt_path=/ckpt/checkpoint_final.pth`
at step 4. Already have the file? Mount it at that path and nothing is downloaded.

Three things about that `docker run` are load-bearing:

| Flag | Why |
|---|---|
| `-v ~/ms3d/ckpt:/ckpt` | Without it the 852 MB re-downloads on every `--rm` run |
| `--shm-size=16g` | Docker defaults `/dev/shm` to 64 MB; PyTorch DataLoader workers crash on it |
| `--user "$(id -u):$(id -g)"` | Otherwise everything written to `/exp` is owned by root |

And create the mount directories *before* the first run, as above: Docker creates
missing bind-mount sources as root, which then defeats `--user`.

## 2. Bring your data

Per subject you need one or more 3D MRI volumes as NIfTI (`.nii.gz`), whether T1,
T1-contrast, T2, FLAIR, or whatever you have, plus a survival label, meaning a
follow-up time and an event/censoring flag, usually sitting in a clinical CSV
keyed by subject id. Step 3 is where you point the tooling at them.

If you're pulling from a public archive such as TCIA and it offers a
pre-skull-stripped NIfTI distribution, take that over DICOM. It lets step 3 derive
brain masks from nonzero voxels instead of running HD-BET.

::: {.callout-tip}
## No cohort of your own? Use RHUH-GBM

[RHUH-GBM](https://www.cancerimagingarchive.net/collection/rhuh-gbm/) (Río
Hortega University Hospital Glioblastoma, on TCIA) fits this walkthrough well:
40 patients with WHO grade 4 astrocytoma, multiparametric MRI, and a clinical
table carrying overall survival alongside an explicit right-censoring flag.

Take the **brain-extracted NIfTI package** (2.9 GB, CC BY 4.0), not the DICOM
one. It arrives co-registered to the SRI24 atlas, skull-stripped with
SynthStrip, intensity-normalised, and resampled to 1 mm isotropic, so step 3's
default `--brain-mask nonzero` is the right setting and HD-BET never has to run.
The DICOM distribution is larger and sits behind an access request. The clinical
CSV downloads separately over plain HTTP.

It unpacks as one folder per patient, three timepoint subfolders each:

```
clinical_data_TCIA_RHUH-GBM.csv
RHUH-0001/
├── 0/   RHUH-0001_0_{t1,t1ce,t2,flair,adc,segmentations}.nii.gz   # preoperative
├── 1/   RHUH-0001_1_...                                           # early postoperative (<72 h)
└── 2/   RHUH-0001_2_...                                           # recurrence / follow-up
```

Step 3 has the flags to consume that nesting directly, and the invocation is
given there. Two things to know before you get to it:

- **Only timepoint `0` belongs in the cohort.** Your prediction origin is the
  scan ([1.3 What is an Event?](../01_background/1.3_what_is_an_event.md)), and
  survival here is measured from surgery, so the postoperative and recurrence
  scans sit *after* the clock starts: a model trained on them is reading the
  future. Including all three would also put one patient in both halves of a
  fold, which is plain leakage.
- **40 subjects, fewer events than that**, makes this a rehearsal cohort, not a
  result. Expect a wide, noisy C-index; step 6 says what to look for instead.
:::

Land everything on the GPU box:

```
$HOME/data/mydataset/
├── raw_nifti/            # per-subject NIfTI volumes
└── clinical.csv          # survival labels
```

Before you script anything against this, look at what you actually have. Folder
nesting and filename conventions vary wildly by source:

```bash
find $HOME/data/mydataset/raw_nifti -name '*.nii.gz' | head -20
head -1 $HOME/data/mydataset/clinical.csv        # see the real column headers
```

## 3. Prepare the dataset

One command turns the folder from step 2 into everything training reads. It
derives case ids from your filenames, stages the nnU-Net layout, makes brain
masks, resamples to a common spacing, crops a fixed field of view, z-score
normalises, writes one `.b2nd` per case, generates the cross-validation splits,
and joins your clinical table into `survival_labels.json`.

Start with `--dry-run`. It does the whole validation pass, meaning id derivation,
the CSV join, and the event mapping, and stops before touching a volume, so it
takes seconds and needs no GPU:

```bash
./.venv/bin/medsurvival3d-prepare \
  --nifti-dir $HOME/data/mydataset/raw_nifti \
  --csv $HOME/data/mydataset/clinical.csv \
  --out $HOME/data/mydataset/survival_dataset \
  --time-col os_days --time-unit days \
  --event-col vital_status --event-values Dead \
  --patch-size 128 128 128 --folds 3 \
  --dry-run
```

```
  nifti-dir: 40 case ids
    TCGA-02-0003, TCGA-02-0006, TCGA-02-0009 (+37 more)
  csv: 43 rows, id column 'subject_id'
  matched: 40/40 case ids
  event mapping
              'Dead' -> 1   (17 cases)
             'Alive' -> 0   (23 cases)
  events observed: 17/40 (42.5%)
  time_years (from days): min 0.21  median 1.84  max 6.03

  dry run: would write 40 .b2nd + labels + 3-fold splits to .../survival_dataset
```

**Read that report.** It is the whole point of the dry run, and it is checking the
two things that otherwise fail silently.

**`matched: 40/40`.** Anything less means your CSV's id column isn't written the
way your filenames are. Fix it with `--id-col` or `--id-regex`. Do not fix it by
renaming files, which puts the ids out of step with everything else. Unmatched
cases are a hard error precisely because the alternative is a crash deep inside a
training run.

**The event mapping.** Every distinct raw value is listed with the label it was
given, so a stray `'Unknown' -> 0` is visible rather than quietly censored.

::: {.callout-warning}
## Check the polarity of your event flag

`--event-values` names the raw values meaning **the event was observed**;
everything else is treated as censored. The default list is
`1, true, yes, dead, deceased, event, 1:deceased`, which is right for a
`vital_status`-style column and exactly wrong for a `censored`-style one, where
`yes` means the subject was *still alive*. For an inverted column, name its falsy
values instead: `--event-col censored --event-values 0,no,false`.

Getting this backwards produces a model that trains happily, reports plausible
losses, and means nothing. You will have taught it to rank the censored subjects
as the high-risk ones. The command warns when every case lands on the same label,
but a plausible-looking mix of 0s and 1s that happens to be inverted will pass
silently. Reading the mapping in the dry-run report is the only real defence.
:::

The proportion of `event == 1` in that report is worth noting now, because it sets
your effective sample size, not your subject count. See
[1.2 Censored Data](../01_background/1.2_censored_data.md).

Then drop `--dry-run` and let it run.

### The flags that depend on your cohort

| Flag | Default | When to change it |
|---|---|---|
| `--id-regex` | whole filename stem | ids need extracting from a longer name. First capture group is the id, e.g. `--id-regex '(.+?)_t1c'` turns `sub-04_t1c.nii.gz` into `sub-04`. Files the regex does not match are skipped, which makes it a filter as well as an extractor |
| `--modalities` | single channel | multi-channel input: `--modalities t1c,flair` in channel order, with `model.input_channels` set to match |
| `--id-col` | tries `subject_id`, `case_id`, `patient_id`, `case`, `id` | your CSV names it something else |
| `--time-unit` | `years` | `days` or `months` |
| `--brain-mask` | `nonzero` | `hdbet` runs HD-BET on non-skull-stripped input; `none` skips masking, which squeezes the volume to `--patch-size` rather than cropping it, distorting the anatomy |
| `--patch-size` | `128 128 128` | must be at least the `data.patch_size` you train with in step 4 |
| `--folds` | `5` | must equal `data.cv.k` in step 4 |
| `--skip-preprocess` | off | rebuild `survival_labels.json` only, after fixing a CSV, without redoing the volumes |

`--nifti-dir` is searched **recursively**, so a source that nests one folder per
subject needs no flattening. That also means every NIfTI under the tree is a
candidate, including segmentation masks and modalities you didn't want, which is
what `--modalities` and `--id-regex` are for.

Uncompressed `.nii` sources are fine: the command symlinks them under `.nii.gz`
names, which the preprocessing filename patterns require while the reader detects
gzip from file contents. Nothing is recompressed.

If your dataset ships a **lesion segmentation** rather than a brain mask, that is
the one case this command doesn't cover: put the segmentation in `nnraw/masks/` and
call `load_crop_brainextract_normalize_images(..., brain_extract=False)` directly,
so the mask picks the crop centre without zeroing everything outside the lesion.

### Doing this with RHUH-GBM

The dataset from step 2 needs three flags to consume its nesting, and each one is
load-bearing:

```bash
./.venv/bin/medsurvival3d-prepare \
  --nifti-dir $HOME/data/rhuh_gbm \
  --csv $HOME/data/rhuh_gbm/clinical_data_TCIA_RHUH-GBM.csv \
  --out $HOME/data/rhuh_gbm/survival_dataset \
  --modalities t1ce \
  --id-regex '(RHUH-\d+)_0_' \
  --time-col <the survival column> --time-unit <days|months> \
  --event-col <the right-censored column> --event-values no,0,false \
  --patch-size 128 128 128 --folds 3 \
  --dry-run
```

- **`--modalities t1ce`** picks which of the six files per timepoint becomes the
  channel. Drop it and they all reduce to the same case id, so channel 0 goes to
  whichever sorts first, which is `adc`, and the other five are counted as
  skipped. The report does print a skipped count and a three-file sample, but it
  never names the file that won, so the numbers look reasonable while the dataset
  holds diffusion maps. T1-contrast is the sequence to reach for first in
  glioblastoma, since the enhancing tumour is what it shows.
- **`--id-regex '(RHUH-\d+)_0_'`** does two jobs. The capture group yields
  `RHUH-0001`, which is how the clinical CSV keys its rows, and the literal `_0_`
  means timepoints 1 and 2 fail to match and are skipped. That is the
  preoperative filter from step 2, expressed as a regex.
- **`--event-values no,0,false`** overrides the default, which includes `yes`.
  RHUH's flag marks patients still alive at cutoff as right-censored `yes`, so
  leaving the default in place would invert every label in the cohort. This is
  the polarity trap above, and here it is the *default* that springs it.

The two column names are left as placeholders on purpose: read them off the CSV
header rather than trusting this page, and confirm whether the survival column is
in days or months before setting `--time-unit`. Then check the dry-run report
says `matched: 40/40` and that the event mapping puts a plausible minority on `1`.

### 3b. Check what it produced

```
$HOME/data/mydataset/survival_dataset/
├── images_b2nd/<case>.b2nd     # [C, X, Y, Z], all modalities stacked
├── splits.json                 # train/val per fold
├── survival_labels.json        # {"<case>": {"event": 0|1, "time_years": <float>}}
└── nnraw/                      # staging symlinks and masks; keep or delete
```

`splits.json` lands at the dataset root, which is where `data/survival.yaml`
already looks, so step 4 needs no `split_file` override.

```bash
./.venv/bin/python - <<'PY'
import json, pathlib
DS = pathlib.Path.home()/"data"/"mydataset"/"survival_dataset"
img = {p.stem for p in (DS/"images_b2nd").glob("*.b2nd")}
lab = set(json.loads((DS/"survival_labels.json").read_text()))
spl = set().union(*[set(f["train"])|set(f["val"]) for f in json.loads((DS/"splits.json").read_text())])
print("images", len(img), "labels", len(lab), "split ids", len(spl))
print("all three id sets identical:", img == lab == spl)
PY
```

The command already guarantees this, so it should print `True`; run it anyway if
you edited anything by hand afterwards.

One thing the command can't check for you: the folds come from a plain shuffled
`KFold`, not stratified on event status. On a small cohort with few events, look at
whether any fold ends up with too few events to compute a meaningful C-index.

::: {.callout-note}
## This step is inside the leakage boundary

Resampling, cropping and normalisation are fit per case here, so they are safe.
Anything you add that is fit *across* cases, such as dataset-level intensity
harmonisation or feature selection, must be fit on training folds only. See the
leakage checklist in [4.1 Survival from Medical Images](4.1_survival_from_medical_images.md#failure-modes).
:::

## 4. Configure and train

Configs ship as package data under `src/medsurvival3d/cli_configs/`. With the
editable install from step 1 you edit them in place and Hydra picks up the
changes live. `CFG=src/medsurvival3d/cli_configs` below just keeps the paths
short.

Start from `survival.yaml`. It's already wired to `SurvivalDataModule`, already
single-channel, already checkpoints on `Val/C-index`. The only thing it lacks is
a loss, which, per [4.1 Survival from Medical Images](4.1_survival_from_medical_images.md#survival-is-a-head),
is the one component that makes this a survival model rather than a classifier.

```bash
CFG=src/medsurvival3d/cli_configs
cp $CFG/data/survival.yaml $CFG/data/survival_mine.yaml
```

::: {.callout-warning}
## Don't start from a `survival_<loss>.yaml`

They carry a loss, but they're wired to a different datamodule
(`COCACombinedB2NDDataModule`), and they all set `save_top_k: 0`, so a run
finishes having saved no checkpoint.
:::

Add the loss under `model:` in `survival_mine.yaml`:

```yaml
  survival_loss:
    name: nll
```

Then change four values:

| Key | Ships as | Set to |
|---|---|---|
| `data.module.name` | `Survival` | `MySurvival` |
| `data.module.data_root_dir` | `${data_dir}/survival_dataset` | `${data_dir}/mydataset/survival_dataset` |
| `data.module.image_dir` | `nnUNetResEncUNetLPlans_3d_fullres` | `images_b2nd` |
| `data.patch_size` | `[160, 192, 192]` | `[64, 64, 64]` |

`data.module.split_file` needs no change: it already points at
`${data.module.data_root_dir}/splits.json`, and that is where step 3 put the file.

Two more depend on your cohort. `data.cv.k` has to match the number of folds in
your `splits.json`; step 3 passed `--folds 3`, so set `data.cv.k` to `3`. (Both
default to `5`; the pair just has to agree, or training walks off the end of the
splits list.)
And `trainer.accumulate_grad_batches` ships at `48`, an effective batch of 96;
on a few dozen subjects that's a wider window than you have batches, so lower it
to something like `4`.

`data.patch_size` must not exceed the `--patch-size` step 3 preprocessed with.
The command prints a `medsurvival3d-train` line with a matching value, if you'd
rather pass these as overrides than edit a config.

::: {.callout-tip}
## Why batch size matters more here than in classification

If you switch the loss to `cox`, effective batch size stops being a tuning knob
and becomes part of the objective: the Cox partial likelihood compares each
subject against the risk set of everyone still event-free, so a small batch is a
poor approximation of that set. `nll` and the other discrete-time losses
decompose per-sample and do not have this problem, a reason they are
the safer default on 3D volumes. See
[2.1 Cox Proportional Hazards Loss](../02_loss_functions/2.1_cox_ph_loss.md) and
[4.1 Survival from Medical Images](4.1_survival_from_medical_images.md#failure-modes).
:::

Finally, point Hydra at writable paths. `$CFG/env/local.yaml` ships with
`/path/to/...` placeholders; replace both:

```yaml
# @package _global_
exp_dir: /home/<you>/experiments/
data_dir: /home/<you>/data/                 # so ${data_dir}/mydataset/... resolves
```

### 4b. Smoke test with `fast_dev_run`

Do this before any real run. It pushes one train batch and one val batch through
the whole graph in about a minute and catches path, shape, and label errors
while they're still cheap.

```bash
WANDB_MODE=offline ./.venv/bin/medsurvival3d-train \
  env=local data=survival_mine \
  data.cv.k=1 data.module.fold=0 \
  model.chpt_path=/path/to/S3D/checkpoint_final.pth \
  model.save_preds=false \
  exp_dir=$HOME/experiments/smoke \
  +trainer.fast_dev_run=true
```

Don't set `seed`. It defaults to `False`, which
keeps `deterministic=False`, and the `avg_pool3d` backward has no deterministic
CUDA kernel, so setting a seed crashes the run.

Success looks like `` `Trainer.fit` stopped: `max_steps=1` reached. `` and exit 0.

### 4c. The real run

Authenticate wandb once with `./.venv/bin/wandb login`, then drop `fast_dev_run`
and the offline flag and keep `cv.k=3` to cross-validate:

```bash
./.venv/bin/medsurvival3d-train \
  env=local data=survival_mine \
  model.chpt_path=/path/to/S3D/checkpoint_final.pth \
  exp_dir=$HOME/experiments/mysurvival
```

`medsurvival3d-train` loops over the `cv.k` folds and streams metrics to the
wandb project set by `trainer.logger.project`, which `survival.yaml` pins to
`Survival`; change it there if you want your own. Checkpoints land at
`${exp_dir}/${teamname}/survival/${data.module.name}/checkpoints/<run-id>/<fold>/`,
so with the command above, under
`$HOME/experiments/mysurvival/debug/survival/MySurvival/checkpoints/`. The best one
per fold is selected on `Val/C-index`. Hydra writes the run's `config.yaml` to that
same `<run-id>` directory, which is what step 6 points at.

## 5. Swapping the loss

The loss comes from `model.survival_loss.name` in your config. Ten are shipped.
This is the head swap of [4.1 Survival from Medical Images](4.1_survival_from_medical_images.md#survival-is-a-head),
exposed as a single config key:

| Name | Family | Covered in |
|---|---|---|
| `cox` | Continuous-time proportional hazards | [2.1 Cox Proportional Hazards Loss](../02_loss_functions/2.1_cox_ph_loss.md) |
| `nll`, `pmf`, `mtlr`, `bcesurv`, `pchazard` | Discrete-time likelihood variants | [2.2 Negative Log-Likelihood Loss](../02_loss_functions/2.2_negative_log_likelihood_loss.md) |
| `deephit` | Discrete-time, ranking-augmented, competing-risk capable | [2.4 DeepHit Loss](../02_loss_functions/2.4_deephit_loss.md) |
| `weibull` | Fully parametric | [2.5 Loss Functions Compared](../02_loss_functions/2.5_loss_comparison.md) |
| `soft_logrank` | Differentiable group-separation surrogate | see the caution below |
| `composite` | Weighted combination of the above | n/a |

::: {.callout-warning}
## `soft_logrank` optimises the picture, not the prediction

Don't reach for it to make a development KM plot look more separated. It
optimises the later visualisation rather than the ranking, adds another weight to
tune, and can overfit whichever grouping rule you happened to pick. Start with a
survival objective, evaluate the continuous score honestly, and choose a cutpoint
afterwards as in [3.3 Kaplan-Meier Curves](../03_metrics/3.3_km_curves.md#choosing-a-risk-threshold).
:::

To try a different one, copy the `model.survival_loss` block from
`$CFG/data/survival_<name>.yaml` into your config. Each block encodes that loss's
own hyperparameters: `deephit` needs `alpha` and `sigma`, `composite` takes a
weighted `components` list with a `primary`, and so on. If you want to
sanity-check the whole install, `fast_dev_run` each loss the way step 4b does.

[2.5 Loss Functions Compared](../02_loss_functions/2.5_loss_comparison.md) compares these on assumptions
and failure modes, which is the better basis for a first choice than sweeping all
ten.

## 6. Reading the results

`Val/C-index`, the checkpoint monitor, is the survival analogue of AUC: the
fraction of comparable subject pairs the model ranks in the correct risk order.
0.5 is chance, 1.0 is perfect ranking. Full treatment in
[3.1 Concordance Index (C-index)](../03_metrics/3.1_c_index.md).

On a small cohort the C-index will be wide and noisy, and a mean near 0.5
usually means too few subjects and events rather than broken code. For a
pipeline check, the right success criterion is a stable, reproducible number
across folds, not a good one.

Keep censoring in mind when you interpret anything. The C-index and the
[KM](../03_metrics/3.3_km_curves.md) and [Brier](../03_metrics/3.2_brier_score.md)
curves the trainer logs all account for right-censoring, but your effective
sample size is the number of observed events, not the number of subjects.

For per-subject risk predictions from a trained checkpoint, use the other console
command, `medsurvival3d-infer` (`src/medsurvival3d/inference/survival.py`, config
`$CFG/inference_survival.yaml`).

Its `exp_dir` is the run's `<run-id>` directory, which holds both `config.yaml`
and one subdirectory per fold containing the `.ckpt` files:

```bash
RUN=$HOME/experiments/mysurvival
UID_DIR=$(ls -d $RUN/debug/survival/MySurvival/checkpoints/*/ | head -1)   # the <run-id> dir

./.venv/bin/medsurvival3d-infer \
  exp_dir=$UID_DIR \
  splits_json=$HOME/data/mydataset/survival_dataset/splits.json \
  pred_dir=$RUN/preds
```

It picks up whichever fold directories are under `exp_dir`, your three, so you
don't pass a fold list. Add `folds=[0,2]` to run a subset.

If it reports finding no fold directories, or `select_best_checkpoint` reports no
checkpoints, `exp_dir` is pointing one level off from the fold directories.

Alongside the per-fold predictions you get `preds/ensemble/test/`. Because each
fold predicts on its own held-out subjects, that table is the pooled out-of-fold
result: every subject scored exactly once, by the one model that did not train on
them. It covers the whole cohort, so it is the number to quote, though it is still
cross-validated, not a held-out test set, which is why its rows are labelled
`split=oof` in `metrics.csv`.

Your `splits.json` has only `train` and `val`, so a request for `test` falls back
to that fold's `val` set. `fold_<k>/val/` and `fold_<k>/test/` therefore hold the
same rows.

::: {.callout-note}
## Next: turning these scores into risk groups
